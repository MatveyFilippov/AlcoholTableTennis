# Архитектура и API

FastAPI, SQLAlchemy и PostgreSQL управляют хронологией и расчётами. React и TypeScript отображают серверные результаты. Caddy обслуживает SPA и проксирует API. Docker Compose запускает сервисы, Alembic управляет схемой.

## Хронология

Транзакция создания игрока, напитка или матча получает исключительную блокировку singleton-строки `timeline_clock` и увеличивает `last_seq`. Чтение берёт разделяемую блокировку и видит согласованный срез. Правки сохраняют `seq` и меняют ревизию. API отдаёт `snapshot_seq` и `projection_version` в формате «номер.ревизия». Время начала — отображаемая метка. Elo использует `seq` публикации.

Снимок матча ограничен текущим номером и номерами создания обоих игроков. Для быстрого ввода нужен свежий снимок. Для Live используется захваченный снимок даже после новых записей. Исправление матча не может менять его снимок. Сервер вычисляет накопление через префиксные суммы активных напитков с `seq <= snapshot_seq`. В PostgreSQL объём и ABV хранятся как NUMERIC с шестью десятичными знаками. При исправлении напитка повторно вычисляются зависимые наблюдения и агрегаты.

Elo начинается с 1000. Вероятность для A равна `1 / (1 + 10^((R_B - R_A)/400))`; изменение равно `32 × (actual − expected)`, одновременно для обоих игроков. История вычисляется из активных матчей по возрастанию `seq` при чтении, с сохранением точности. Равенство Elo разрешается по имени и UUID для стабильного отображения.

## Контракт REST

Базовый путь `/api/v1`. Swagger и OpenAPI доступны локально с `ATT_DOCS=1`. Записи идентифицируются UUID. Публичные POST требуют заголовок `Idempotency-Key` с UUID. Повтор того же тела возвращает сохранённую запись, изменённое тело под тем же ключом даёт 409.

| Метод и путь | Назначение |
| --- | --- |
| GET `/state` | Вечер, снимок, ревизия, игроки, матчи, напитки, короткие факты, порядок сравнения |
| GET / POST `/players`, GET `/players/{id}` | Игроки и профиль |
| GET / POST `/drinks` | Журнал и добавление напитка. Фильтр `player_id` |
| GET / POST `/matches`, GET `/matches/{id}` | Результаты. Фильтры `player_id`, `opponent_id`, `target`, `oldest` |
| GET `/match-publication` | По UUID в заголовке `Idempotency-Key` возвращает `{match_id}` либо null |
| GET `/leaderboard`, `/analytics/overview`, `/analytics/players/{id}` | Рейтинг, итоги и аналитика игрока |
| GET `/analytics/head-to-head?player_a=…&player_b=…` | Личные встречи |
| POST `/admin/login`, `/admin/logout`; GET `/admin/me` | Сессия администратора |
| GET `/admin/records`, `/admin/audit` | Записи, включая удалённые, и аудит |
| PATCH / DELETE `/admin/{entity}/{id}`; POST `/admin/{entity}/{id}/restore` | Правка, удаление, восстановление с `row_version` |
| POST `/admin/matches/{id}/preview` | Предпросмотр изменения Elo в откатываемой транзакции |

Матч принимает `player_a_id`, `player_b_id`, `target`, `score_a`, `score_b`, `snapshot_seq`, `a_intoxication`, `b_intoxication`, опциональный `started_at` и `mode` (quick/live). Напиток принимает `player_id`, `name`, `volume_ml`, `abv_percent`.

Наблюдение содержит `match_id`, `seq`, `opponent_id`, `actual`, `expected`, `residual`, `ethanol_g`, `self_rating`, `elo_before`, `elo_after`. `player.comparison` содержит `n`, `omitted`, `start`, `end`, `delta`. Половина содержит W–L, долю побед, средние expected, residual и `mean_ethanol_g`. При числе матчей меньше четырёх обе половины и delta равны null. `comparison_order` — UUID сопоставимых игроков, отсортированные сервером по delta, имени и UUID.

Администратор использует серверную сессию с Secure HttpOnly SameSite cookie. Изменяющие запросы требуют `X-ATT-Admin: 1`. Ссылки на активную историю блокируют удаление игрока. Ошибки API имеют код, русское сообщение и request ID.

## Переход со схемы 0001

Ревизия 0002 удаляет только таблицу `stages` и `stage_id` из напитков и матчей вместе с их FK и индексами. Номера событий не уплотняются. Исходные записи, UUID, снимки, аудит (включая старый JSON), сессии и ключи повторов сохраняются. Обратное заполнение удалённых полей невозможно без дампа. Перед обновлением существующей БД нужен бэкап. Процедура восстановления описана в runbook.

Черновик v1 преобразуется в v2 с сохранением UUID запроса, участников, очков, снимка, времени и самооценок. Для v1 с pending клиент сначала проверяет ключ через `/match-publication`. Если ключ найден, черновик закрывается. Если ключ отсутствует, пользователь подтверждает публикацию с новым форматом. Сам статус не создаёт записей. Старый ключ по-прежнему блокирует POST с несовпадающим телом.
