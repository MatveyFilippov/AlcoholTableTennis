## 1. Задача и ограничения проекта

Разработать современный веб-сайт для компании друзей, позволяющий вести статистику настольного тенниса **в рамках одного непрерывного игрового вечера**: фиксировать сыгранные матчи, употребление алкоголя, собственную оценку опьянения, рейтинг Elo и его изменение относительно других игроков. Количество игроков заранее неизвестно. Возможен участник, сыгравший единственный матч с одним соперником.

Приложение публично доступно в интернете и **не требует регистрации для обычных действий**. Изменять/удалять уже сохранённые записи может только администратор с единственным паролем. Участники осознанно делают публичными свои псевдонимы и всю информацию о напитках, объёмах, крепости и субъективной оценке состояния.

**Принцип:** сайт показывает наблюдаемые статистические связи, а не утверждает, что алкоголь стал причиной выигрыша/проигрыша. Не рассчитывать «промилле крови» по объёму напитков и не давать рекомендаций по дозам алкоголя.

## 3. Ключевые пользовательские сценарии

**Сценарий A — начало игры.** Пользователь открывает пустой сайт, видит краткое объяснение, добавляет Rick, Morty и Summer. Приложение изначально содержит только системный этап №0 «Трезвые». Elo всех новых игроков начинается со 1000, но новичков без матчей нельзя выдавать за лидеров рейтинга.

**Сценарий B — трезвые игры.** Указывают участников, формат до 11, счёт 11:8. Подтверждают результат. Система начисляет победу/поражение, обновляет общий и трезвый Elo, показывает матч в истории. Если играли снова до 21 — регистрируют ещё один отдельный матч.

**Сценарий C — употребление.** Создают «Раунд 1». Указывают, что Rick выпил 500 мл пива 5%, Morty — другой напиток, Summer не пила. Это три **разных состояния**; создание раунда не означает, что все выпили. В течение вечера добавляют следующие раунды и напитки без сброса сумм.

**Сценарий D — матчи после употребления.** Перед матчем для обоих игроков указывают субъективное состояние 0–10, либо явно «неизвестно». Сохраняют счёт. В статистике матча остаются и эти оценки, и накопленное количество этанола на момент начала игры.

**Сценарий E — Live.** Выбирают пару/формат, нажимают большие кнопки начисления очка, при ошибке используют Undo. Счёт до завершения виден только на устройстве. Обновление вкладки не теряет локальный черновик. После финального подтверждения создаётся **один** матч; повторная отправка после сетевой ошибки не дублирует результат.

**Сценарий F — изучение итогов.** На главной видны лидеры, рейтинг и изменения; в профиле игрока — победы, личные встречи, динамика Elo, выпитое и связь результата с состоянием. При одной игре система не создаёт ложный вывод о зависимости от алкоголя.

**Сценарий G — исправление.** Записали 11:7 вместо 11:9. Обычный посетитель исправить уже сохранённое не может. Администратор входит по паролю, исправляет результат; все последующие рейтинги автоматически пересчитываются, действие фиксируется в журнале.

## 4. Модель данных и неизменяемая хронология

Минимальные сущности: `tournament` (единственный), `player`, `stage`, `drink_event`, `match`, `timeline_clock`, `audit_log`, `admin_session`, `idempotency_record`. Возможна нормализованная структура с дополнительными таблицами, если она проще поддерживается. PostgreSQL — единственный источник истины.

**Обязательные идентификаторы:** UUID для сущностей; UTC для сохранённого времени; `timeline_seq` — уникальный целочисленный номер опубликованного события (включая создание игрока; выдаёт сервер транзакционно). Порядок матча для Elo определяется номером **публикации**, а не локальным временем браузера. Пользовательское `started_at` носит справочный характер.

- Игрок: UUID, отображаемое имя, нормализованное имя с защитой от дубликатов, цвет/инициалы, **seq создания**, created_at, archived_at, версия записи.
- Этап: порядковый номер, название, seq и время создания. Этап №0 создаётся автоматически. Новые этапы не порождают новые турниры.
- Напиток: игрок, этап, название, мл, ABV%, seq, метаданные удаления. Процент ABV и объём хранятся без потерь исходных значений.
- Матч: два **разных** игрока, целевое число 11/21, два счёта, этап, seq публикации, `snapshot_seq` состояния при начале игры, самооценки A и B (`0..10 | null`), дата, статус мягкого удаления, версия.
- Аудит: тип операции, кто администратор (сессия), старое и новое значение, дата; без хранения секретов.

**Важный edge case:** Live-матч начали до того, как записали новый напиток, но опубликовали результат уже после напитка. У матча должен сохраниться snapshot состояния **на начало**, а не на момент сохранения счёта. Для этого перед стартом счётчик читает у backend `snapshot_seq` и хранит его локально. Backend при публикации вычисляет накопленный этанол по событиям с `seq <= snapshot_seq`; затем присваивает самому матчу новый номер публикации. Такой механизм не требует общего Live-состояния на сервере.

Коррекция старого напитка может изменить состояние более поздних матчей, а коррекция старого матча — все последующие Elo. **Нельзя просто перезаписать одну строку и оставить прежние производные значения.** Проекции должны пересчитываться детерминированно из исходных событий. Удаление — мягкое (`soft delete`) с возможностью восстановления. Удаление игрока или этапа, на который ссылаются матчи/напитки, нельзя превращать в каскадную потерю истории: блокировать с понятной ошибкой, а игрока при необходимости архивировать.

## 5. Валидация матчей

Матч всегда 1 на 1. Минимум 11 или 21, победитель обязан опережать на 2 очка. Кроме того, итоговый счёт не может быть таким, при котором игра **уже должна была закончиться раньше**.

Валидные примеры: **11:8**, **11:9**, **12:10**, **13:11**, **21:19**, **22:20**, **23:21**. Невалидные: **11:10**, **12:9** (закончилась бы 11:9), **15:11** (закончилась бы 13:11), **21:20**, **22:18**, отрицательные/дробные очки, одинаковые игроки.

Формально: выигравший счёт `W >= T`, `W-L >= 2` и `(W == T либо (L >= T-1 и W == L+2))`, где `T ∈ {11,21}`. Не допускаются ничьи, технические поражения, doubles, best-of-сеты.

Счёт матча влияет на Elo только через факт победы/поражения. До 21 не должно автоматически давать вдвое больше рейтинга. Очки могут отображаться в дополнительной статистике.

## 6. Учёт напитков и самооценка

Точный расчёт при заданном объёме и крепости: `этанол_г = объём_мл × ABV_% / 100 × 0.789`. Пример: 500 мл × 5% ≈ **19.725 г** этанола. Это лишь расчёт принятого этанола; **не** оценка концентрации алкоголя в крови и **не** оценка реакции человека.

Рейтинг опьянения на матч: целое число **0–10**, отдельно для каждого игрока; допустимо `null` («неизвестно»). Ноль означает явно подтверждённое «трезв»; отсутствие информации нулём не считается. На начальном этапе №0 значения 0 заданы исходной предпосылкой «все трезвы». Для новых этапов можно предлагать последнее значение, но не подставлять его незаметно.

Показывать накопленный этанол (г) по каждому человеку и каждому этапу, журнал всех напитков (имя, объём, крепость, время), рядом — самооценки для сыгранных матчей. Пустая или неизвестная оценка не должна «превращаться» в 0 на графике. Можно не вводить напитки, но записывать субъективное состояние — показатели остаются независимыми.

## 7. Elo: конкретный алгоритм

**Начальный рейтинг:** 1000. **K-factor:** 32, постоянный. Для каждого завершённого матча в порядке `match.seq` перед расчётом считываются **предматчевые** рейтинги обоих участников:

```text
E_A = 1 / (1 + 10 ^ ((R_B - R_A) / 400))
S_A = 1, если A победил, иначе 0
R_A_new = R_A + 32 * (S_A - E_A)
R_B_new = R_B + 32 * ((1 - S_A) - (1 - E_A))
```

Оба рейтинга обновлять **одновременно по исходным значениям**. Внутри расчёта не округлять; округление — только в UI. Для 1000 против 1000 победа A даёт **1016 vs 984**.

**Трезвый Elo** — абсолютно отдельная последовательность со стартом 1000 и K=32, обновляется **только** когда у **обоих** игроков известная самооценка 0 и накопленный этанол на начало матча также равен 0. Номер этапа сам по себе не доказывает трезвость. При отсутствии трезвых матчей вместо уверенной цифры показывать «Нет данных».

У игроков с менее чем пятью матчами — пометка «Предварительный рейтинг». Игроки с нулём матчей не должны автоматически возглавлять рейтинг. При одинаковом Elo применить стабильный tie-break. На графике учитывать, что рейтинги могут изменяться у разных участников в разном количестве игр.

## 8. Аналитика алкоголь/результативность

Создать независимые представления:

1. **Общий рейтинг:** таблица Elo, выигрыши/проигрыши, Win Rate, изменение позиции после матчей, график двух выбранных участников.
2. **Трезвый рейтинг:** отдельная таблица и число допущенных трезвых матчей.
3. **Личные встречи:** A против B, все счёты, W/L и количество игр; при отсутствии встреч вывод «Нет личных встреч».
4. **Алкоголь:** накопленный этанол (г), динамика самооценки 0–10, этапы, совпадение с матчами; отдельные фильтры по игроку.
5. **Performance vs Expected:** по предматчевым Elo рассчитать ожидаемую вероятность победы A, затем `остаток = фактический результат (0/1) – ожидаемая вероятность`. Показать средний остаток и количество наблюдений в группах по самооценке **0**, **1–3**, **4–6**, **7–10**, **неизвестно**.
6. **График:** этанол (г) по оси X и остаток по оси Y (scatter), фильтры по игроку/этапу, аккуратные подсказки с количеством игр и соперником.
7. **Корреляция Spearman (желательно):** только минимум при восьми пригодных матчах и трёх разных уровнях самооценки; иначе «Недостаточно данных». Корректно учитывать совпадающие ранги и отсутствие дисперсии.

**Обязательная подпись:** «Связь не доказывает причинность: на результат влияют соперник, усталость и случайность». Не вычислять фиктивное изменение «силы на 40%» и не выдавать рейтинг за лабораторную оценку влияния алкоголя. Средняя результативность зависит от того, против кого человек играл. Фильтры и размер выборки видны всегда.

## 9. Страницы

- **Главная `/`:** минимум вступительного текста, текущий этап, число участников/матчей, лидерборд, понятный график Elo и последние результаты; акцентное действие «Записать матч».

- **`/alcohol`:** этапы, быстрое добавление напитка, публичный журнал и диаграммы.
- **`/analytics`:** сравнения, Elo, трезвые показатели, связь алкоголя с результатом.
- **`/admin`:** пароль, административные исправления/удаления/восстановление, журнал правок.

На всех страницах: мобильная навигация, нормальные пустые состояния, статус сохранения, ошибки сети, понятные надписи, аккуратный 404. Не прятать основные действия в декоративных анимациях.

Агент волен использовать **любые полезные skills**, библиотеки и UI-инструменты. Необходимо качество результата, а не соответствие конкретному набору tools.

## 12. API и серверная логика

Основной контракт REST `/api/v1`: `GET /state` (текущий этап и snapshot seq), `GET/POST /players`, `GET/POST /stages`, `GET/POST /drinks`, `GET/POST /matches`, `GET /matches/{id}`, `GET /leaderboard`, `GET /analytics/*`, `POST /admin/login`, `POST /admin/logout`, `GET /admin/me`, административные `PATCH/DELETE` и восстановление сессией администратора, журнал аудита. Health: `/api/health/live` и `/api/health/ready`.

Все POST, которые создают записи, должны поддерживать `Idempotency-Key`. Повторная отправка того же payload с тем же ключом возвращает уже созданный результат; другой payload с тем же ключом — `409`. Все входные параметры проверяются сервером. Для конфликтующих админских правок — `row_version`/optimistic concurrency. Ошибки в машиночитаемом формате и понятном русском тексте. API-документация через OpenAPI.

**Никакой авторитетной математики Elo на frontend.** Вычисления, хронология, валидация и агрегаты находятся на backend. Frontend — ввод, визуализация и локальный черновик счётчика.

## 13. Минимальная безопасность и сохранность данных

Это сайт для друзей, поэтому не нужно переусложнять вход и защиту от злоумышленников. **Но** публичная форма в интернете не должна позволять случайно стереть всю историю или отправить невалидный матч.

- Любой может **создавать**, только администратор **править/удалять**. При опасном действии — диалог подтверждения и понятные последствия.
- Административный пароль из secret, не в коде; сессия Secure/HttpOnly/SameSite; базовые ограничения попыток входа. Никаких стандартных паролей.
- Валидация чисел, UUID, времени, имён и длины строк. Простейшее ограничение частоты записи, без CAPTCHA и тяжёлого anti-spam.
- Аудит исправлений, мягкое удаление, backup перед релизом, тест восстановления в отдельную БД.
- Никаких credentials в публичном GitHub, клиентском JS, логах или `.env.example`.
- Публичность алкогольной информации объяснить пользователям при добавлении игроков/напитков; рекомендовать псевдонимы.

## 14. Git и правила для Codex

Владелец создаёт и настраивает репозиторий; **Codex не создаёт новый**. Базовая рабочая ветка — `dev`; любые ветки агента — **`codex/*`** от актуальной `dev`, например `codex/feat/att-mvp`.

- `main` — рабочий production source, прямой push запрещён, только PR с успешными проверками.
- `dev` — интеграционная; изменения по возможности только через PR.
- Работа агента: создать `codex/*`, реализовать и локально протестировать, выполнить Conventional Commits, запушить свою ветку, открыть **PR в `dev`**, приложить результаты проверок и снимки экрана.
- Затем **владелец** принимает PR, делает отдельный `dev → main` PR и публикует Release. Агент не мержит и не деплоит.
- Использовать `AGENTS.md` как долговременные правила проекта.

**Запрещено:** прямой SSH или любой прямой production deployment через Codex Work, создание нового репозитория вместо существующего, пуш в `main`/`dev` вместо PR, сокрытие падающих тестов и утверждение об успешном деплое без проверки.

## 15. Проверки CI и деплой

**CI на PR (`dev`, `main`):** backend unit/integration с PostgreSQL, frontend unit, ESLint/Ruff/type checking, Playwright, сборка двух Docker images и проверка Compose. Имена jobs должны быть стабильны для настройки GitHub Rulesets. Любая неудача блокирует merge.

**Push в `main`:** собрать и опубликовать GHCR-образы `web`/`api` с неизменяемой меткой SHA коммита; **не выполнять деплой**.

**Published GitHub Release:** автоматический deployment только для стабильного `vMAJOR.MINOR.PATCH`, не draft/prerelease, и только если tag указывает на **актуальный HEAD `main`**, его CI успешен и образы с таким SHA уже собраны. GitHub Environment `production`, секреты только там. Обновление через SSH **из GitHub Actions**, а не из Codex. Образы устанавливать по digest, использовать блокировку параллельных релизов.

Порядок: проверить условия → проверить pull образов → резервная копия PostgreSQL → совместимая миграция БД → обновление web/api → health checks + HTTPS smoke → зафиксировать версию. Ошибка — автоматический откат **только образов, если схема БД обратно совместима**. Небезопасное восстановление БД — исключительно вручную по runbook; перед релизом нужен backup, с проверкой пригодности.

**Развёртывание на чистом Ubuntu 24.04 выполняется владельцем:** установка Docker/Compose, пользователь deploy, SSH ключ, Firewall, каталог `/opt/att`, `.env`/секреты, открытые 80/443 и рабочий SSH, GHCR packages access, GitHub Environment. Codex подготавливает все скрипты и инструкции, но не выполняет настройку сервера напрямую.

## 16. Обязательные тесты и критерии приёмки

| ID | Проверка |
|---|---|
| AC-01 | На пустой БД создаётся ровно один турнир и системный этап «Трезвые» без поддельных игроков/матчей |
| AC-02 | Создаются 3+ игрока, в т. ч. участник с единственным матчем; статистика не ломается |
| AC-03 | Валидные 11:8, 12:10, 21:19, 23:21 принимаются; 11:10, 12:9, 22:18 и одинаковые игроки отвергаются backend |
| AC-04 | Быстрый ввод и Live-счётчик создают один матч; до подтверждения Live нет записи в БД |
| AC-05 | После reload Live-черновик восстанавливается; Undo и двойная отправка работают корректно |
| AC-06 | 500 мл 5% ≈ 19.725 г, отрицательные объёмы/ABV отклоняются; значения самооценки только 0–10 или null |
| AC-07 | Этап не заставляет всех «выпить», у трезвого игрока 0 независимо от других |
| AC-08 | Поздний напиток не попадает в snapshot ранее начатого Live-матча |
| AC-09 | Первый Elo для пары 1000/1000 при победе A равен 1016/984; обе стороны обновляются по pre-match рейтингу |
| AC-10 | Sober Elo получает только явно трезвые матчи обоих участников; unknown не считается трезвым |
| AC-11 | Исправление старого матча/напитка админом пересчитывает зависимую историю детерминированно |
| AC-12 | У 0–1 матчей аналитика не обещает статистически обоснованной корреляции; нет NaN/Infinity |
| AC-13 | Публичные POST работают, публичные PATCH/DELETE закрыты; админ умеет корректировать и восстанавливать |
| AC-14 | Интерфейс профессиональный светлый, работает на 320/390/1440px, без горизонтального скролла, доступны keyboard/focus/reduced-motion |
| AC-15 | Все CI-проверки зелёные на PR, запущены настоящие E2E с БД, PR из `codex/*` направлен в `dev` |
| AC-16 | Обычный push/PR не деплоит; только корректный опубликованный Release текущего main проходит deploy guard; backup/health/rollback документированы |

Проверки с конкретными fixture-данными и отрицательными сценариями — в `docs/TEST_PLAN.md`. Нельзя считать задачу выполненной только потому, что код компилируется.

## 17. Что не нужно делать в первой версии

Несколько игровых вечеров/турниров; регистрация и социальные аккаунты; doubles; best-of серии; общий Live через WebSockets; offline synchronization; предсказания BAC, «идеальной дозы» и медицинские выводы; платёжная система; реклама; глобальная многоуровневая админ-панель; Kubernetes; тяжёлые ML-модели; моковые графики на production.

Полезные улучшения (экспорт CSV/JSON, светлая/тёмная тема с поддержкой тёмной как P1, PWA-иконка, расширенные фильтры) допустимы **только после** исправного выполнения P0 и тестов.

## 18. Что Codex обязан передать в PR

1. Полную рабочую реализацию в `codex/*` с PR **в `dev`**, исходным кодом и миграциями.
2. Корректные `README.md`, `AGENTS.md`, `.env.example`, architecture/API/docs, локальный запуск через Docker Compose, инструкции разработчика.
3. Реальные тесты, отчёт о запущенных командах и их результатах, фиксированные тестовые данные (только для тестов), E2E, сборки образов.
4. Скриншоты **светлого** интерфейса в мобильном и десктопном размерах и описание UX-решений.
5. GitHub workflows для CI, GHCR image build и release-only deploy; скрипты backup/upgrade/health/rollback.
6. Инструкцию владельцу для одноразовой настройки VPS/GitHub Secrets/Environment/Rulesets и первого Release; без секретов внутри репозитория.
7. Список архитектурных компромиссов, известных ограничений, технического долга (если есть). Недоделки нельзя объявлять завершёнными.

**Definition of Done:** код работает и проходит проверки локально/в CI; PR создан и открыт в `dev`; все внешние задачи владельца прозрачно перечислены. Фактический production-deploy **не входит** в работу Codex Work и не должен заявляться выполненным до отдельного Release и GitHub Actions.
