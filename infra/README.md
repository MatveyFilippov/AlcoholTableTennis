# Развёртывание ATT

## Один раз перед первым релизом

1. После первого запуска CI включите обязательный PR и проверки `backend-tests`, `frontend-tests`, `e2e`, `docker-build` в правилах для `dev` и `main`. Запретите удаление и force push. Объедините изменения через PR в `dev`, затем через отдельный PR из `dev` в `main`.
2. Дождитесь зелёных **CI** и **Publish images** на одном коммите `main`. Включите публичную видимость GHCR-пакетов `alcoholtabletennis-web` и `alcoholtabletennis-api` или настройте на сервере отдельный доступ на чтение обоих пакетов.
3. На Ubuntu 24.04 установите Docker Engine и Compose v2.30 или новее по [инструкции Docker](https://docs.docker.com/engine/install/ubuntu/). Проверьте DNS A/AAAA, доступность 80 и 443, свободное место и рабочий SSH-порт. Доступ к Docker даёт полномочия уровня root. Используйте выделенный deploy-аккаунт на выделенном VPS и отдельный SSH-ключ.
4. Создайте `/opt/att`, `/opt/att/releases`, `/opt/att/backups`, доступные только deploy-аккаунту и системному администратору. Создайте `/opt/att/.env` с правами 0600 и строками `APP_DOMAIN=att.ricksanchez.ru`, `POSTGRES_USER=att`, `POSTGRES_DB=att`, `POSTGRES_PASSWORD=<сгенерированный пароль>`. Для пароля подойдёт вывод `openssl rand -hex 32`.
5. Запустите `python -m att.hash_password` из `backend/` в окружении с зависимостями проекта. Перенесите только хеш в `/opt/att/admin.env` с правами 0600 в строке `ADMIN_PASSWORD_HASH=<хеш>`. Формат файла сырой, кавычки не нужны. Для opaque-сессии отдельный `SESSION_SECRET` не используется. Образы workflow передаёт по digest.
6. В GitHub создайте Environment `production`. Ограничьте развёртывание тегами версий. Ограничьте создание, изменение и удаление тегов `v*` правилами GitHub для доверенных владельцев релизов. Настройте `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_PRIVATE_KEY`, `DEPLOY_KNOWN_HOSTS` и при необходимости `DEPLOY_PORT`. Сверьте ключ хоста через доверенную консоль VPS. Ключ хоста для нестандартного порта должен иметь формат `[hostname]:port`.
7. На текущем HEAD `main` опубликуйте GitHub Release `v1.0.0`. В Actions проверьте создание дампа, миграцию, digest обоих образов и ответ HTTPS с версией коммита.

## Обновления

Публикуйте стабильный Release на текущем HEAD `main` после успеха CI и публикации обоих образов. Push в `main` публикует образы с SHA-тегом. Workflow релиза проверяет тип события, тег, коммит, зелёные запуски обоих workflow и наличие digest. Перед SSH он повторно сверяет `main` и тег. Вход на VPS использует pinned known_hosts. На сервер загружается версия Compose и скриптов из проверенного коммита.

Ревизия 0002 меняет контракт приложения и необратима. Для чистого первого релиза прежней версии приложения нет. Если на стенде уже работает 0001, запланируйте окно обслуживания. Workflow остановит старые web/API перед резервной копией и не запустит прежние образы поверх несовместимой схемы. При сбое после миграции используйте проверенный дамп и отдельную БД.

Последующие миграции должны оставаться совместимыми с текущей версией приложения. Сначала добавляйте новые поля и таблицы, переносите данные, затем переключайте чтение и запись. Удаление полей и другие несовместимые операции требуют отдельного плана. Проверяйте `alembic upgrade head` на чистой БД и копии прежней схемы. Автоматический откат приложения рассчитан на совместимую схему.

## Сбой релиза

- По выводу Actions определите этап сбоя. При ошибке guard проверьте SHA тега, SHA `main`, результаты push workflow и GHCR. Если тег уже устарел, создайте новую стабильную версию на текущем `main`.
- На VPS проверьте `docker ps`, логи сервисов, свободное место и `/opt/att/active.env`. Этот файл хранит SHA, тег, два digest и каталог манифеста последнего здорового приложения. Путь к резервной копии указан в логе релиза.
- После неудачной проверки readiness скрипт пытается поднять прежние совместимые образы и завершает workflow с ошибкой. После неудачной первой установки web и API останавливаются. Состояние PostgreSQL сохраняется.
- Для ручного отката совместимого приложения на VPS вызовите `/opt/att/releases/<каталог>/scripts/rollback.sh --compatible-schema-confirmed` после проверки совместимости. Скрипт использует `previous.env`. Для дальнейшего релиза выпустите новую версию с текущего `main`.

## Резервное копирование и восстановление

Перед каждой миграцией создаётся custom dump PostgreSQL с временем UTC, SHA релиза и ревизией схемы. Скрипт проверяет размер и оглавление архива. Храните последние 14 копий, отмечайте нужные для восстановления и переносите их в закрытое хранилище вне VPS. Ротация ручная. Дампы содержат персональные записи и хеши сессий.

Проверка копии: запустите `scripts/restore-rehearsal.sh /path/to/backup.dump`. Скрипт поднимает отдельный временный контейнер и выводит ревизию и количество записей. Для дампа `empty` в первом релизе таблиц ещё нет, используйте дамп с рабочей схемой для полноценной проверки. Сравните данные с моментом копирования и проверьте чтение и статистику тестовым API перед восстановлением.

При необходимости восстановления БД остановите запись, сохраните текущий том и дамп, разверните выбранный бэкап в **новой** БД и проверьте его с совместимой версией приложения. Переключите рабочие сервисы на новую БД только после проверки. Сохраните исходный том до подтверждения восстановления. Смена БД может исключить записи, сделанные после резервной копии.
